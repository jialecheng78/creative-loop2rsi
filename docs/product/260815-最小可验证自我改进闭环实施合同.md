# Creative RSI Studio 最小可验证自我改进闭环实施合同

## 结论

应用版首个 RSI 验收不以“模型自己说变好了”为成功，而以一条可复核的完整因果链为成功：

```text
3 项独立作品出现同一条直接用户反馈
→ 独立 Candidate Builder 生成声明式创作指导候选
→ targeted / regression / held-out 各一次盲比
→ 用户明确采用
→ active method version 改变
→ 第 4 项作品实际绑定并使用新指导
→ 旧方法仍可回退
```

这条链称为“最小可验证自我改进”。它证明应用能从跨作品反馈中提出、评价、采用并实际使用一个新方法，但不等于正式 L4，也不等于模型权重自改或完整自主 RSI。

## 为什么与正式 L4 分层

现有 `loopctl.py` 的正式 L4 晋升要求先以证据达到 L3，包括至少 5 个样本、Producer/Judge 校准、局部恢复和多 Loop 证据。为了演示而降低这些门槛，会让成熟度标签失真。

应用首版因此维护两条状态轴：

| 状态轴 | 作用 | 首版允许改变 |
|---|---|---|
| 正式成熟度 | L0–L5 的可证明系统成熟度 | 不因最小闭环自动升级 |
| active method version | 应用当前使用的声明式创作指导 | 通过本合同的三组盲比与人工采用后改变 |

## 证据门

### 1. 重复问题

- 至少 3 个不同 `work_id`、`run_id` 和任务；
- 只采信用户直接提交的 `feedback_text`；
- v1 只自动聚合规范化后完全相同的反馈，不声称理解同义改写；
- 同一作品反复修改不能凑数；
- 每条来源绑定反馈 receipt、作品 artifact、任务 receipt 与封存 manifest 的 SHA256。
- 三项来源必须属于同一基线 epoch。epoch 固定绑定 `method_version`、requested/returned model、`system_fingerprint`、DSH Profile SHA256 与模型参数摘要；任一字段变化都建立新观察，不得把旧 finding 与新作品混算为三个独立证据；
- 旧 epoch 的 finding 和反馈永久保留，但只作为历史证据展示，不会因新 epoch 再次物理复制或重复计数。

### 2. 候选构建

- Builder 使用独立 DSH Candidate Worker；
- Builder 只读取初始创作方向、三条已封存反馈、基线指导和允许修改面；
- held-out 任务在候选冻结后才创建，绝不进入 Builder 上下文；
- 输出只允许是一条声明式创作指导，不执行模型生成代码；
- 候选生成时记录 requested/returned model、`system_fingerprint`、Profile 和请求账本。
- Builder、三个来源作品和四次盲比生成必须与候选冻结的 epoch 一致；三项来源 provenance 必须全部复核，不能只检查被选作 targeted / regression 的两项。

### 3. exact-three 盲比

固定三组且各一次：

- `targeted`：验证候选是否解决重复反馈指向的问题；
- `regression`：在第二个冻结来源作品上观察候选是否产生明显非劣化；v1 尚无“用户已保留的干净回归锚点”，因此该组不能被表述为正式全量回归；
- `heldout`：用候选生成后才创建的新任务验证迁移能力。

每组向用户只展示随机化的 A/B 作品，不展示哪一份使用候选。用户可选 A、B 或“差不多”。三组评价必须使用不同 task/context id，且作品与选择均不可覆盖。

每组不可变 `AppMethodBlindDecision` 是该组选择的提交点，候选状态只是可重建投影。若进程在写入决定后、更新候选状态前中断，重启后的快照和采用操作必须从三份决定重新推导 `EVALUATING / READY_FOR_HUMAN / BLOCKED`，不得要求用户覆盖或重复提交已经冻结的选择。

### 4. 采用门

只有同时满足以下条件才显示“采用新方式”：

- targeted 选择候选；
- regression 选择候选或差不多；
- held-out 选择候选或差不多；
- 三组输出使用同一 model 与 `system_fingerprint` 基线；
- 用户明确点击采用。

采用先写入不可变 PromotionReceipt，再更新 Controller 管理的 active method registry。只有“PromotionReceipt 已提交、registry 仍指向前一稳定版本且没有后续 rollback receipt”的窗口可标为 `adoption_pending` 并允许完成同一次采用。拒绝、盲比失败或已经显式回滚的候选不能改变当前方法；v1 不允许把已回滚候选无新凭证地重新激活。

### 5. 实际生效与回滚

- Production Worker 每次创作前从 Controller 获取当前 method context；
- 非基线方法必须验证候选、三组评价、人工采用凭证和注册表哈希；
- `begin_work`、WorkTaskReceipt 与 RuntimeProvenance 必须绑定 method version 和 context SHA256；
- 采用后的第一项新作品是“实际使用新方法”的验收作品；
- 回滚只移动 active method pointer，保留候选、评价、采用和回滚全部历史。
- 回滚 receipt 是“该候选已退出生产”的显式证据；回滚后的 `PROMOTED` 候选属于历史版本，不得在界面上显示为“等待完成采用”。

## 用户界面

普通用户只看到：

1. “它学到了什么”：展示重复反馈和独立作品数；
2. “新方式”：准备候选、完成三组盲比、查看结果并采用或拒绝；
3. “版本”：当前方法、历史采用记录和回退按钮。

不向普通用户展示 finding code、Prompt、DSH Profile、Schema、eval run id 或哈希。失败提示必须说明下一步，不能把候选生成失败描述为作品丢失。

## 模拟真人验收

独立任务只使用打包后的应用和 Computer Use，不读取仓库或修改代码。固定验收过程：

1. 创建一个创作方向；
2. 完成 3 个不同任务，并对每个冻结作品提交同一条明确反馈；
3. 在“新方式”中生成候选并完成三组盲比；
4. 只有确实更好或不劣时采用；
5. 完成第 4 个任务，确认版本页与治理记录都显示新方法被使用；
6. 执行一次回滚并确认历史证据仍在。

测试身份必须写作 `simulated-user`，不得冒充真实非程序员测试。程序最多允许 5 个修复迭代；超过后停止并交付根因与下一步计划。

## 首版不证明

- 不证明正式 L4 成熟度；
- 不证明模型 Judge 已完成校准；
- 不证明语义相近但措辞不同的反馈会被正确聚类；
- 不证明文学质量普遍提升；
- 不证明系统可修改或晋升 Controller、Judge、DSH Runtime 或应用代码；
- 不证明 Windows 安装、签名、公证或无警告安装。
