# 预览包发布树合同

## 目标

无签名预览包只能包含运行所需字节、许可证与可复核来源证据。构建机的安装状态、本机路径或私有软件源不属于产品运行输入，不得进入 app bundle、Windows unpacked 目录或其 manifest。

## 发布树门禁

- `pnpm deploy` 产物在进入 Electron 包前必须删除 package-manager 的锁文件、工作区配置、安装状态、package map、PnP/integrity 状态和调试日志；运行所需的 `package.json` 不在此列。pnpm workspace/install state 的带版本文件名和 npm/pnpm/yarn debug/error log 也按模式拒绝，不只依赖单个已知文件名。
- deploy 收口必须递归覆盖 Desktop 与全部 production dependencies，删除运行时不需要的 `.d.ts` / `.d.mts` / `.d.cts` 声明和 source map。只在 `node_modules` dependency subtree 中删除标准 `README*` / `CHANGELOG*` / `HISTORY*` / `CONTRIBUTING*` / `CODE_OF_CONDUCT*` / `SECURITY*` 等依赖说明文档，以及精确命名为 `test` / `tests` / `__tests__` / `spec` / `specs` 的目录和 `.(test|spec).(js|cjs|mjs|ts|tsx)` 文件。测试目录判定不得跨越 dependency package entry 边界：`node_modules` 的 unscoped package child 和 scoped namespace 下的 package child 即使名为 `test` / `tests` / `spec` / `specs` 也必须保留，只有进入该 package root 后的同名内部目录才可删除。app 自身的同名资产、`LICENSE*` / `LICENCE*` / `NOTICE*` / `COPYING*`、非标准命名的运行时 Markdown、`.js`、`.json`、native addon 和其他运行资产必须保留。
- 对必须保留的 JavaScript / CSS 源文本，收口只能通过语法 scanner 与 parser-aware AST comment ranges 定位单行或块注释 token，并且只将注释 token 内的 generic home 前缀归一为无本机信息的占位符。注释外的代码、字符串和其他运行字节必须原样保留；其中的 home 路径仍必须由审计拒绝。改写必须使用同目录临时 regular file、保留 mode 并 atomic rename，不得原地改写可能存在的 hardlink。
- 最终发布树必须通过 fail-closed 审计：出现 package-manager 元数据路径、macOS/Linux/Windows 形式的用户 home 绝对路径（包含 `file:///` / `webpack:///` 本地 URI）、package-store 绝对路径，或不在明确公共允许列表内的 registry 配置时，构建立即失败。当次构建机的 exact home（包含文件内恰好以 home 结尾的情况）与 package-store 针对所有 regular-file 原始字节扫描；不依赖已知用户名的通用路径、registry 和 package-store 规则，只对扩展名在允许列表（包含 Python、Shell、PowerShell 与 Windows batch 源文件）、UTF-8 严格可解码且不含 NUL/非文本控制字符的 text-like 文件执行。registry 必须是明确允许 host 的精确 `https` 根 URL，不得使用 bare host 或其他协议，也不得含端口、userinfo、子路径、query 或 fragment；JSON 转义斜杠、Unicode 转义斜杠、YAML inline/block 与 TOML `[registries]` 中的 `default` 写法同样受检查。
- Registry 审计只把明确 registry 配置且值为 literal string、URL 或 bare registry host 的 assignment 当作候选。代码中的表达式赋值和类型成员不是 registry metadata；Controller sidecar 源码不能因变量名包含 `registry` 而被删除或误报。
- 审计覆盖最终 Electron 发布树，包括 Desktop payload、Controller sidecar、Electron runtime、许可证和来源证据；不能只审计源码树或 deploy 中间目录。
- 所有 symlink 的原始 target 必须是相对路径，必须能 strict 解析，且最终解析位置仍位于发布树内；指向树内的绝对 target 与 broken symlink 也必须拒绝。
- macOS 与 Windows 的 Node CI 必须在 frozen workspace install 后、运行 Desktop 安全测试前显式物化 lockfile 固定的 Electron runtime。安全测试只验证已安装 runtime 的 Renderer/Preload 隔离边界；不得在有界启动测试窗口内隐式下载 Electron，也不得把 CI 冷启动超过五秒误判为隔离失败；Linux 无界面矩阵不做这一步。

## Manifest v2

`StudioPreviewBuildManifest` 与 `ControllerSidecarBuildManifest` 的 `schema_version` 固定为 `"2"`。

Controller sidecar 的临时构建树必须创建在最终输出目录的同一父目录中，确保 Windows runner 即使系统临时目录与仓库位于不同盘符，最终 `os.replace` 仍是同卷原子移动。临时树必须使用唯一名称，并在成功或失败后清理；不得退化为跨卷复制后再删除，也不得覆盖既有输出或 manifest。

排序 inventory 必须包含发布树根目录 `.`、每个目录、regular file 与 symlink。每个条目绑定相对路径、类型和目标平台 mode；此外：

- regular file 绑定字节数与 SHA256；
- symlink 绑定原始相对 target。

macOS 目标的 `mode` 是包含前导零的四位 POSIX 八进制字符串，例如 `"0755"`；Windows 不使用 POSIX 执行位，因此根目录和所有条目的 `mode` 均固定为 `null`。macOS app 主入口与 Controller sidecar 主入口必须是 mode `"0755"` 的 regular file；Windows 则绑定两个 `.exe` 入口的字节和 `mode: null`。

Studio 的 `tree_sha256` 根据排序后的完整 v2 inventory 计算；改变 regular-file 字节、symlink 目标，或任一受治理条目的 POSIX mode 都会改变树哈希。旧 v1 manifest 不能用于新预览包。

## macOS alpha 发布封装合同

- 发布构建必须由固定版本 pnpm 脚本发起。`npm_execpath` 可以是常见的全局 pnpm 启动符号链接，但构建器必须先以 strict `realpath` 将它解析为存在的 regular file，并在版本校验、store 查询与后续内层构建中只使用该已解析目标。broken link、目录、非绝对路径或版本非 `11.7.0` 均必须 fail closed。
- macOS arm64 bundle 在生成 manifest 前必须完成全部可变字节：替换为项目自有 `CR` 图标，删除 Camera、Microphone、Bluetooth 与 Audio Capture 等未使用的 `Info.plist` 隐私声明，再安装 Desktop payload、Controller sidecar、许可证与来源证据。Apple bundle 字段固定为纯数字 `CFBundleShortVersionString=1.0.0` 和 `CFBundleVersion=1`；产品预发布身份 `1.0.0-alpha.1` 继续由 package、source identity、delivery manifest、附件名与 tag 精确绑定。
- 发布 SBOM 与许可证的 source of truth 是最终 App 中实际分发的闭包：`Contents/Resources/app` 内真实存在的 package tree、Electron runtime 身份及 notice，以及 Controller sidecar manifest 声明的 runtime component 及 notice。不得以 workspace root 的 `pnpm --prod` 结果代替发布闭包，也不得把未进入 App 的 build-only 组件列入发布 SBOM。
- Electron 发布证据必须绑定 Electron `43.4.0` 及其内嵌 Node.js、Chromium 的实际 runtime 版本。在 seal 前必须将 Electron 分发物的 `LICENSE` 和 `LICENSES.chromium.html` 安装到 App，并以相对路径、bytes 与 SHA256 绑定；这些 notice 不得在 seal 后补写。
- Controller sidecar 必须分发 CPython 与 PyInstaller 的适用 notice，并在 sidecar manifest 的 `runtime_components` 中绑定实际版本、许可证标识、notice 相对路径、bytes 与 SHA256。alpha.1 只接受 CPython `3.11.x` 与 PyInstaller `6.22.0`。
- Node 组件闭包必须从最终 App payload 递归枚举真实 package root，绑定每个 `package.json` 与同 package 下 `LICENSE*` / `LICENCE*` / `NOTICE*` / `COPYING*` 的 SHA256；必须包含五个 DSH `0.1.0-rc.6` 直接组件以及 App 内实际分发的 production dependency 闭包。证据只保留 App/证据树内相对路径和内容哈希，不得写入 workspace、pnpm store、Python 环境或临时目录的本机路径。
- alpha 的 CycloneDX/许可证据粒度固定为最终 App 的 physical npm package roots 与显式 runtime components。canonical notice mapping 必须以最终 deployed physical closure 为条件：target 不存在时不得从 ambient workspace/pnpm store 复制 notice、生成 provenance 或把组件写入 SBOM；target 存在时则必须对其每个 physical root 继续执行 source、notice 与 provenance exact-set 门禁。只有最终 App 实际分发 `@img/sharp-libvips-darwin-arm64`，才额外生成 sharp/libvips aggregate declarations，并必须绑定其 pinned `README.md` 许可表与 `versions.json` 的原字节/SHA256：如实保留 README 的 29 条上游许可声明，并绑定 `versions.json` 实际提供的 28 个版本键。README 额外声明的 `libnsgif` 没有对应版本键，证据必须标为上游未声明版本，不得猜测。这不等于为 aggregate 内每个内嵌库交付了逐组件完整许可证文本；该 component-level license completeness 是仅在分发该 aggregate 时适用的 alpha 已知非阻断缺口，SBOM、Release 说明和 notice 都不得越界宣称“完整许可证闭包”。
- bundle 所有字节就绪后，固定执行匿名 ad-hoc seal：`/usr/bin/codesign --force --deep --sign - --timestamp=none`，并立即以 `/usr/bin/codesign --verify --deep --strict` 验证。该 seal 不得被描述为 Developer ID 签名或 Apple 公证。发布封装还必须独立确认 `Signature=adhoc`、`TeamIdentifier=not set` 且无 `Authority`，再优先读取 `spctl --raw`。raw plist 只接受 Apple 实际输出的结构：顶层 `assessment:authority` dictionary，其内 `assessment:authority:flags=0` 且只可选包含 `assessment:authority:source`，顶层另有 boolean `assessment:remote` 与 `assessment:verdict=false`；未知 key、未知 value type/value、错误 nesting 或额外诊断都必须 fail closed。只有明确返回 `no usable signature` 才记为 `REJECTED_UNSIGNED_EXPECTED`；系统 raw plist 无 source/reason 且 stderr 只有裸 `rejected` 时必须记为 `REJECTED_ADHOC_UNATTRIBUTED`，不得伪造拒绝原因。旧系统不支持 `--raw` 时，非 raw 裸 `rejected` 仍按同一状态分类。任何 damaged、malware、revoked 或其他 source/reason 都必须 fail closed。seal 之后不得再改写 app bundle 内任何字节。
- `StudioPreviewBuildManifest` 必须在 strict codesign 通过后从最终 bundle 重新生成，并明确绑定 `developer_id_signed=false`、`notarized=false`、`adhoc_sealed=true` 与 `strict_codesign=PASS`。
- 公开主附件固定为 macOS-aware ZIP，使用 `/usr/bin/ditto -c -k --keepParent --norsrc --noextattr --noqtn --noacl --nopersistRootless` 创建；ZIP 内只允许一个 `Creative RSI Studio.app`。必须从 ZIP 解压到新临时目录，对解压树重做完整 inventory，与 app manifest 逐项精确相等，再次通过 strict codesign，并由该解压 App 完成 `credential=not-configured` 且 `model_requests=0` 的 packaged smoke。delivery manifest 只能绑定这次解压后 smoke 结果。
- 发布输出目录、主 ZIP、证据 ZIP、`SHA256SUMS.txt` 或任一临时构建目标已存在时必须 fail closed，不得覆盖。证据 ZIP 只包含 app/sidecar manifest、path-free delivery manifest、CycloneDX SBOM、脱敏许可证目录、精确 Git source archive 及其 manifest。
- `ReleaseDeliveryManifest` 只允许使用相对发布文件名和与机器无关的身份字段，必须绑定 version/tag/platform/minimum macOS、commit/tree、主 ZIP 的 bytes/SHA256、app/sidecar/source/SBOM/licenses 证据哈希、strict codesign、ZIP round-trip 与 packaged smoke 结果。由于 delivery manifest 本身位于 evidence ZIP 内，不得伪造对自身容器的递归哈希；evidence ZIP 的 bytes/SHA256 由外部 `SHA256SUMS.txt` 绑定。manifest 不得包含本机绝对路径、Key、userData、用户作品、日志或运行状态。

## 对用户的影响

界面和创作流程无变化。收口后的预览包不再泄露构建机路径或内部软件源，且可以证明 macOS 主程序与 sidecar 的执行权限未被篡改。

第三方二进制可能保留上游编译机调试路径；这不等于当次构建机泄露。这类文件不跑通用文本 regex，但仍受当次构建机 exact 原始字节针、固定依赖版本、SHA256 和 mode 绑定。
