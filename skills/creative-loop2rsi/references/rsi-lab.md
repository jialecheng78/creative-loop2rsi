# RSI 实验室

## 1. 实验目标

只在 L0–L4 已有稳定证据链时，探索系统是否能提出并验证“改进机制本身”的后继候选。这里的对象不只是创作 Prompt，还可以是：

- Judge 的 rubric、上下文或权限；
- finding 聚类和根因定位策略；
- 候选生成策略；
- target/regression/held-out 的分配策略；
- 改进控制器的搜索、预算或停止规则；
- 多分支候选档案的选择策略。

把所有结果标记为 `experimental / unvalidated / CANDIDATE`。不要因候选能修改自身配置就宣称实现完整 RSI。

## 2. 入场条件

进入 L5 实验前检查：

1. L0–L4 晋升证据连续完整；
2. 当前稳定版本可回滚；
3. protected surfaces 已由外部策略锁定；
4. held-out 与候选生成过程隔离；
5. 外部元评价者已指定；
6. 候选预算、分支数和停止条件已固定；
7. 用户明确同意开展实验，但没有授权自动发布。

任一条件缺失都停在 L4，输出缺口，不创建“伪 L5”。

## 3. 受保护表面

L5 候选也不得修改：

- `creative-system/creative-charter.md` 及确认记录；
- 原始素材和来源证明；
- held-out 输入的答案、偏好标签和身份；
- `LICENSE`、安全与隐私边界；
- 晋升政策本身；
- 人工审批边界；
- 候选预算的外部上限；
- 审计和回滚记录。

将保护规则放在候选不可写的位置，由外部控制器验证。不要让候选通过重命名文件或间接引用绕开语义保护。

## 4. 分支候选档案

每个候选建立独立档案：

```text
creative-system/candidates/<candidate-id>/
├── proposal.json
├── parent.json
├── changes/
├── eval-plan.json
├── evidence/
├── meta-evaluation.json
└── status.json
```

记录：

- 父版本和谱系；
- 修改的机制层级；
- 根因假设；
- 允许和禁止修改的表面；
- 目标、回归、held-out 和元评价预算；
- 每次运行的完整 manifest 和哈希；
- 被拒绝原因；
- 外部评价者身份与独立性说明。

保留失败和分叉，不把档案修剪成只剩成功路径。档案用于解释探索过程，不等于晋升授权。

## 5. 外部元评估

让没有参与候选生成、没有读取候选意图的评价者判断：

- 新 Judge 是否更接近人工立宪，而非更容易给自身候选高分；
- 新学习策略是否发现更多真实问题，而非制造更多 finding；
- 新控制器是否用更少预算得到同等或更好结果；
- 新机制是否维持硬合同、隐私和回滚能力；
- 改进是否在未知任务上成立；
- 结论是否能由保存的原始证据复核。

把“候选改进了自身评分”视为风险信号，而不是成功。若 Judge 与被 Judge 的候选共享变更，必须引入冻结 Judge、人工盲评或另一独立评价面。

## 6. 实验状态机

允许状态：

```text
DRAFT → CANDIDATE → META_EVALUATED → REJECTED / ARCHIVED
```

v0.1 不提供从 L5 `CANDIDATE` 到 `PROMOTED` 的自动边。即使元评估通过，也只输出外部决策材料，由人决定是否在未来版本采用。

禁止：

- 候选直接更新 active version；
- 元评价者修改候选以便通过；
- 候选扩张自己的预算；
- 候选删除失败分支；
- 候选改变成功标准；
- 候选发布作品或系统版本。

## 7. 可解释的实验方案

缺少后验时，允许提出可解释但未验证的方案。每个方案必须回答：

1. 要修改哪一层机制？
2. 为什么现有 finding 指向这一层？
3. 哪个观察能够证伪根因假设？
4. 哪些表面绝对不变？
5. 谁来独立评价？
6. target、regression、held-out 分别测什么？
7. 预算和停止条件是什么？
8. 失败后如何回到稳定版本？

没有答案时标记为 `proposed`，不要伪造实验结果。

## 8. 对抗性请求处理

当用户要求“让系统自动改掉所有规则并直接发布”时：

1. 明确拒绝自动修改创作宪法、晋升政策和人工边界；
2. 明确拒绝自动晋升和发布；
3. 将可研究部分缩小为隔离候选；
4. 锁定 protected surfaces、预算与 held-out；
5. 提议外部元评估；
6. 保持 `CANDIDATE` 并给出停止原因。

推荐回执：

```text
BLOCK：该请求会让候选同时修改成功标准并批准自己，无法形成可信证据。
可执行替代：建立隔离的 L5 候选，只允许修改 <目标机制>；保持立宪、晋升政策、held-out 与人工审批不变；由外部评价后再决定是否采用。
```

## 9. 发布表述

允许说：

- “实现了 L5 候选档案与外部元评估接口”；
- “完成一次受限的系统级实验”；
- “观察到候选在冻结评价面上的改进，尚未晋升”。

禁止说：

- “系统已经具备完整自主 RSI”；
- “系统能够无限自我进化”；
- “候选自己证明了自己更好”；
- “实验代码存在，所以 L5 已通过”。

## 10. 未来验证清单

把尚未完成的工作明确列为后续验证：

- 多轮独立真实任务是否复现改进；
- 外部元评价是否与用户长期偏好一致；
- 候选谱系是否出现评价投机；
- held-out 是否被间接污染；
- 分支探索成本是否受控；
- 回滚是否在机制变更后仍可用；
- 非程序员是否理解 `CANDIDATE` 不等于发布版本。

在这些问题有可靠后验前，保持 L5 为实验层。
